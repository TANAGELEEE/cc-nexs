# Write a New Preset

Follow the steps in this document to customize a preset for a new stack / new team / new workflow.

## Decide Whether to Write a New Preset

| Your Need | Recommendation |
|---------|------|
| Tweak stack-check rules, build commands, templates, or role prompts | Copy `preset-standard` and modify it |
| Introduce a new role (e.g. SecurityAuditor) | Add it to an existing preset |
| Switch tools (use Gemini instead of Codex) | Just change `roles.definitions.<role>.tool` in preset.yml |
| A different document set or gate layout | Redesign preset.yml, templates, and commands; the core state machine supports `lean` and `hotfix` |

## Getting Started
```bash
cd packages/
cp -r preset-standard preset-myteam
cd preset-myteam
```
Changes:

1. **`package.json`** —— change the name to `@cc-nexs/preset-myteam`
2. **`preset.yml`** —— see the schema below
3. **`agents/*.md`** —— change the identity prompt, inject stack-specific features
4. **`templates/*.md`** —— change the templates to match your documentation conventions
5. **`i18n/<locale>/strings.json`** —— localize user-visible text
6. **`commands/*.md`** —— modify the phase commands so they reference this preset's agents

## preset.yml field quick reference
```yaml
name: preset-myteam            # kebab-case
version: 0.1.0
description: 一句话说明
language: zh-CN | zh-TW | en-US  # default locale

roles:
  enabled:                     # 状态机按角色名分派
    - lean-planner
    - lean-plan-reviewer
    - lean-developer
    - lean-reviewer
    - lean-verifier

  definitions:
    lean-planner:
      agent: agents/lean-planner.md  # 相对 preset 根目录
      tool: claude-subagent     # claude-subagent | codex | gemini | openai-cli | custom
      alias: Planner            # 可选：UI 显示名
      session_isolation: independent  # 强制独立 session

    lean-developer:
      agent: agents/lean-developer.md
      tool: claude-subagent
      alias: 工程师

    # 自定义角色
    security-auditor:
      agent: agents/security-auditor.md
      tool: codex
      alias: 安全审计

stack:
  type: java-maven | node-pnpm | python-poetry | rust-cargo | go-mod | generic
  build_cmd: "mvn compile -q"
  test_cmd: "mvn test"
  lint_cmd: "checkstyle ..."
  src_paths:                    # glob 模式，hooks 用它判越权
    - "src/main/**"
    - "src/test/**"
  forbidden_patterns:           # 代码层面的禁令
    - regex: "[一-龥]"
      excludes: ["//", "/\\*", "log\\."]
      description: "代码内禁中文字符串"
    - regex: "\\bTODO\\b"
      excludes: []
      description: "禁 TODO 提交"
  custom_review_rules:          # 字符串，注入 reviewer prompt
    - "禁止使用 @Autowired"
    - "Service 不写 Interface + Impl"

paths:
  doc_dir: "doc/{id}.{slug}/"
  branch_pattern: "feature/{id}-{slug}"
  bugs_dir: "bugs/"

workflow:
  default_mode: lean
  thresholds:
    review_revision: 3
    fix_per_bug: 3

i18n:
  conclusion_pass: "PASS"
  conclusion_fail: "NEEDS_REVISION"
  test_pass: "通过"
  test_fail: "阻塞"
```
## plugin.json metadata

The preset source uses `.claude-plugin/plugin.json`, not the legacy `manifest.json`. Only metadata such as the name, description, and license is maintained here; do not list core commands/agents, and do not write `../core/...` paths. `pnpm build` materializes the core and preset contents into a self-contained `dist/preset-myteam/` while also syncing the root marketplace.
```json
{
  "name": "cc-nexs-myteam",
  "version": "0.1.0",
  "description": "cc-nexs preset for my team",
  "license": "MIT",
  "keywords": ["claude-code", "plugin", "workflow"]
}
```
To support Codex, also maintain the Codex UI metadata in `.codex-plugin/plugin.json` and pin `"skills": "./codex-skills/"`; these skills are generated by the build from the same set of authoritative commands, so do not hand-write copies. Before running the build/three-target validation, you must add `preset-myteam` to the root `release-presets.json`, because the build only accepts explicitly listed release presets.

## Role agent file skeleton
```markdown
---
name: <role-name>
description: <一句话>
tools: Read, Write, Edit, Glob, Grep, Bash
allowed_read:
  - spec.md
  - <其他允许读的相对 doc 目录的路径>
allowed_write:
  - spec.md
forbidden_read:
  - src/**
forbidden_write:
  - progress.md
---

你是 <role-alias>。<role-name> 在本项目的职责是 <...>。

## 身份纪律
1. ...
2. ...

## 输入
- doc/<id>/...

## 产出
- doc/<id>/...

## 完成后
仅写入产出文件，不输出额外摘要。orchestrator 会自动推进。
```
The `allowed_read / allowed_write / forbidden_read / forbidden_write` fields are parsed by `core/lib/role-registry.mjs::allowedFiles()`, and hooks use them to block unauthorized access.

## Custom hooks

If the 3 hooks in core are not enough, a preset can add its own:
```json
{
  "hooks": {
    "PreToolUse": [
      ...core hooks...,
      {
        "matcher": "Bash",
        "command": "node -e \"const p=require('node:path'),u=require('node:url'),r=process.env.PLUGIN_ROOT||process.env.CLAUDE_PLUGIN_ROOT||process.env.CC_NEXS_PLUGIN_ROOT;if(!r)process.exit(1);import(u.pathToFileURL(p.join(r,'hooks','my-custom-check.mjs')).href)\""
      }
    ]
  }
}
```
Write to `packages/preset-myteam/hooks/`, following the stdin JSON / exit 0|2 protocol. Do not
use `${VAR:-fallback}` in hook commands: it is POSIX shell syntax and is not portable in Windows
PowerShell or `cmd.exe`. Use `process.env` in the Node launcher
to resolve the plugin root directory.

## Verification
```bash
# 1. preset.yml schema 校验
node packages/core/lib/validate-json.mjs \
  packages/core/schemas/preset.schema.json \
  packages/preset-myteam/preset.yml

# 2. plugin metadata + 全量生成物
node -e "JSON.parse(require('fs').readFileSync('packages/preset-myteam/.claude-plugin/plugin.json'))"
pnpm build
node scripts/validate-claude-plugins.mjs
node scripts/validate-codex-plugins.mjs
node scripts/validate-pi-package.mjs

# 3. hook 语法检查
node --check packages/preset-myteam/hooks/*.mjs 2>/dev/null || echo "no custom hooks"

# 4. 装载测试：只装 build 后的自包含 dist，不直接 symlink packages 源码
pnpm install:local
# 在测试项目中跑 /cc-nexs:status 验证 plugin 被识别
```
## Returning a new preset to the monorepo

If your new preset is a good fit for contributing back as open source:

1. It is automatically included by the existing `packages/*` glob in `pnpm-workspace.yaml`
2. Add `preset-myteam` to the root `release-presets.json`
3. Add a row to the preset table in the root `README.md`
4. Open a PR against the cc-nexs main repository

## Localization and template overlays

Presets support `en-US`, `zh-CN`, and `zh-TW` runtime strings. The project language and `CC_NEXS_LOCALE` template selector are separate settings: set both when you want runtime messages and generated templates to use the same locale. Put locale-specific strings in `i18n/<locale>/strings.json`; the core locale file is loaded first and preset strings override it.

Templates use the same optional overlay convention. Place a complete or partial template tree under `templates/<locale>/` (for example, `templates/zh-TW/lean/requirements.md`) and set `CC_NEXS_LOCALE=zh-TW` before running initialization. Initialization defaults to `en-US`; missing files fall back to the preset's default `templates/` tree, so a locale can be added incrementally without changing the workflow or machine-readable contracts.
